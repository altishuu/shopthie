# Area 11 — Owner safety investigation and stop gate

**Decision: blocked; no Owner-safety migration or guard has been installed.** Repository inspection does not establish a safe, enforced lock protocol across all account, membership and provider-deletion entry points. No hosted/provider/native access was made during this investigation. This is a source audit, not a live catalog readback or a concurrency proof.

## Existing boundary observed in the migration chain

- `20261028145618_authority_foundation.sql:57-65` defines one membership per account, with `app_accounts.user_id REFERENCES auth.users(id) ON DELETE CASCADE`, and `app_user_roles.user_id REFERENCES app_accounts(user_id) ON DELETE CASCADE`. The role reference has the default NO ACTION, not a role-delete cascade. Thus a real Auth-user deletion can reach the application account and membership through two declared database FK cascades; the actual hosted catalog and provider deletion implementation were not inspected here.
- The same migration enables RLS and revokes all private-table privileges from PUBLIC, anon and authenticated (lines 91–98); authenticated receives schema usage and narrowly granted functions, not raw authority-table DML. This describes migration-defined ACLs, not a current hosted-catalog proof. Provisioning (`:68-79`) is an Auth-insert trigger that creates an active account and **Customer** membership, with no Owner bootstrap.
- `20261029165555_customer_status.sql:6-30` guards account revision and immutable subject but does not protect the last Owner or account deletion. `:37-60` attaches a membership/profile BEFORE ROW trigger that acquires the parent account `FOR UPDATE`, tolerating an absent parent on DELETE for cascades; it does not count Owners. `:187-227` is the existing status writer: it locks actor and target parent rows in UUID order and only changes a current Customer; it cannot be counted as an Owner-management path. Repository searches of `src` and `supabase` found no additional direct application-account/membership writers or Auth admin deletion call, beyond provisioning, this status writer and the declared cascades. Privileged SQL/operator/provider writers are not exhaustively enumerable from source, and table owners or sufficiently privileged administrators can bypass ordinary ACL/trigger assumptions.
- Profile/address writers and audited lookup/status/support reads also lock parent account rows; see `20261028181746_profiles.sql:52`, `20261029031614_addresses.sql:108,202`, `20261029165555_customer_status.sql:86-89,155-156,199-200`, and `20261104120706_profile_support.sql:52,121`. The existing Area 8 documentation explicitly warns that child-row triggers do not enforce parent-first ordering for arbitrary trusted direct child writes (`docs/backend-customer-status-database.md:13-19`).

## Why a partial guard is unsafe

1. Counting remaining Owners in per-row triggers without common transaction serialization permits two independent removals of different active Owners to observe each other and both commit, leaving zero. A single-session PGlite test cannot establish safety against that race. Zero Owners at installation must still be allowed; the rule must prevent a transition from a positive count to zero, not reject an already-empty database or create an Owner.
2. A BEFORE ROW membership trigger is too late to impose a universal pre-lock protocol: direct UPDATE/DELETE can already hold the child tuple before the trigger waits for the parent. A concurrent parent-first account operation or cascade can hold the parent and wait for that child, creating a lock cycle. Existing documented parent-prelocking is an operator convention, not enforced for every privileged entry point.
3. Merely adding a global transaction/advisory lock in an application-table BEFORE STATEMENT trigger also does not establish a global order across the existing application. For example, the customer-status RPC can hold a parent account lock before reaching its UPDATE statement; another direct membership statement could first acquire the global lock and then wait on that parent in the existing membership trigger. The RPC can then wait for the global lock, creating a cycle. Other prelocked account/profile/address paths and cascades must be analyzed too; putting a lock on only destructive row triggers does not resolve them.
4. Auth deletion starts outside the application tables and can already hold an Auth-user row lock before its FK cascade enters application triggers. A solution must cover that actual entry point and its order relative to existing parent/child and provisioning paths, not assume an application API was called first. Provider Auth DDL/mutation is explicitly out of scope, and provider deletion behavior/permissions were not queried. It is therefore not established that every such entry can be made to pre-acquire the same serialization lock without widening this slice.
5. A guard also needs a sound snapshot/isolation strategy, complete bulk and cascading statement handling, rollback, ACLs and a defined privileged-operator boundary. Client raw-table denial alone does not prevent privileged direct writes, TRUNCATE, trigger disabling, or provider-owned behavior. Do not describe a guard as universal unless its defined trusted boundary and bypass protections are independently verified.

## Required work before reconsidering implementation

- Define and enforce a complete transaction-level lock order covering every participating privileged writer, existing prelocking RPC, direct account/membership mutation, Auth deletion cascade and bulk operation; explicitly identify any necessarily excluded superuser/owner powers. Resolve the provider entry-point constraint without changing provider Auth DDL, or obtain a separately approved scope change.
- Prove positive-to-zero prevention, existing-zero installability, rollback, both cascade paths, raw-role denial and no implicit Owner assignment against actual SQL roles. Exercise destructive operations against synthetic data only.
- Use at least two independent real PostgreSQL sessions to demonstrate simultaneous different-Owner races and lock-order/deadlock cases under supported isolation levels; test aborted transactions and all mixed entry paths. Review exact ACLs, RLS, triggers, FKs, functions and provider integration before any hosted apply. Local PGlite is available, but no `psql`, `postgres`, `initdb`, `pg_ctl`, Docker or Podman executable was found on PATH in this environment.
- Application-row protection, even if eventually correct, cannot prove prevention of provider bans, MFA/factor or verification changes, email changes, authentication failure, or recovery loss. Positive native Owner/MFA/provider acceptance requires separate authorization and remains deferred.

No tests or migrations were added; no concurrency or native acceptance is claimed. Area 10 files and the Git index were not intentionally modified.
