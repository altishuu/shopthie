# Area 13 — implement first-Owner setup only

## Authorization and stop gate

User authorized continuation after the recommendation to implement first-Owner bootstrap only, with **no live activation**. This area delivers production application/database code and local verification, not another prototype. Do not execute hosted DDL or designate/promote any real subject without separate approval after review. No real account/status/role/MFA/session changes, Owner replacement, factor recovery/removal, staff management, email/signup changes, paid services, commits/pushes or frontend deployment. Preserve all currently staged Area12 work and the index. No application-source copies/snapshots/archives/manifests.

## Operational flow

1. A trusted database operator explicitly designates one active confirmed-email Customer using a fresh opaque approval-reference UUID. No identity is chosen during this implementation. Designation grants no application privilege and cannot replace an already consumed bootstrap. Only the marker/schema owner or superuser may execute operator procedures; not application Owner/Admin/Customer, anon, authenticated or service_role. Database role plus opaque approval reference is operator attribution within this database; separate protected human approval evidence remains mandatory.
2. The designated account can visit `/account/owner-setup`, optionally verify its already enrolled authenticator through the existing official self-MFA transport, then explicitly consent. Enrollment remains on existing `/account/security`; no factor deletion/cancellation or recovery path is added. No hidden automatic consent or role change.
3. A self-consent RPC derives subject/session from provider-verified request claims, requires native active/confirmed/not-deleted/not-banned Customer, current verified TOTP, a current AAL2 session bound to that factor, native JWT `aal2`, integer `amr` TOTP authentication within5minutes and valid `exp`. Untrusted form/metadata cannot supply assurance, actor, target, proof time, factor or session evidence. Intent expiry must not exceed proof freshness or token expiry. Store private session/factor UUIDs but never tokens, passwords, OTPs or setup secrets. Return only minimal self state and opaque intent reference/expiry.
4. A separate trusted operator explicitly activates the exact designation/intent/approval reference. Revalidate all live account/session/factor/designation/expiry gates, consume once, require zero Owners and unconsumed global singleton, atomically promote exactly one Customer with mandatory minimal audit, re-arm the unchanged restrictive freeze and preserve ordinary Customer RPCs. No UI/API endpoint can grant ownership. No activation command will be run against hosted data here.

## Database contract

- Candidate `supabase/migrations/20261106020000_owner_bootstrap.sql`; all prior installed SQL remains immutable. Native catalog-only preflight confirmed PostgreSQL17.11, postgres executor, Auth users/sessions/factors SELECT+UPDATE privileges, expected UUID/enum/time columns, zero Owners, one freeze marker and four ALWAYS guards. No native rows/identifiers or credentials retrieved.
- Dedicated optional enabled module `owner_setup`, dependencies identity/access/audit. Permission `owner.bootstrap.request_own`, Customer-only, self-scoped. Broader staff/support unchanged. Default installation has no designated identity; bootstrap is closed until explicit operator designation. Required audits cannot be disabled.
- Private singleton control/designation and private intents: RLS, no raw client grants, no client read of other subjects/session/factor/operator references. Completion tombstone prevents a second bootstrap even if a future trusted operator removes Owners. Designation may be changed only before consumption; rotating its UUID invalidates prior intents. No client selector decides the target.
- Public RPC `shopthie_owner_bootstrap_state()` returns JSON exactly `{subject, status, designation}` with subject current UUID, status one of `unavailable|mfa_required|ready|consented|completed`, designation UUID or null. For a current consented designation it may additionally return `intent` exactly `{id, expiresAt}` with canonical UTC timestamp; otherwise no intent property. Null/no authenticated subject denies. No email/phone/username/factor/session/operator reference in DTO. Wrong/not-designated callers receive unavailable, no indication of another subject. Completed can be reported only to the activated self; no control data leakage.
- Public RPC `shopthie_owner_bootstrap_consent(p_designation uuid)` returns the same exact DTO with consented+intent after committed audit. No subject/assurance/session/factor/time parameters. Bind p_designation to current control/current UID, fail closed on stale or malformed. Idempotent repeat must not add audits or silently renew stale proof; never auto-retry writes in UI.
- Private SECURITY INVOKER trusted-operator functions: `designate_first_owner(p_subject uuid,p_approval_ref uuid)` returns designation UUID; `activate_first_owner(p_designation uuid,p_intent uuid,p_approval_ref uuid)` returns void. Explicit ACL revocation and effective-grant checks across nontrusted roles, ownership/RLS prerequisites and empty search paths. No permanent bootstrap privilege granted to app/service roles.
- Mutation functions require READ COMMITTED and use SQL lock_timeout/statement_timeout plus NOWAIT acquisition. Activate locks app_accounts/app_user_roles/cutover marker and control; locks exact Auth user/session/factor rows using FOR SHARE NOWAIT (no provider table-wide locks/DDL). Establish deterministic ordering/try-lock failure rather than waiting through conflicting provider deletes. All relevant validations occur under locks and again after mandatory audit if necessary. Do not consume intent or return consent if audit was suppressed.
- Atomic activation temporarily disables only membership row freeze while app tables are AX-locked; promotes target, renews private marker via TRUNCATE+reinsert, restores membership guard ENABLE ALWAYS, marks control/intent consumed and audits before commit. No account/membership TRUNCATE, blanket Customer freeze, setting-based public bypass or unsafe comparator modes. Rollback includes marker storage, trigger modes, role, tombstone and audits. Validate exact expected guard ownership/definitions/modes and effective ACLs before trusted transition, not only at installation.
- Minimal event types `owner.bootstrap.designate`, `owner.bootstrap.consent`, `owner.bootstrap.activate`, fixed reason `initial_owner_setup`. Self consent actor=current UID; trusted operator audit actor=null with operator reference/actual DB executor held in private control/intent, never fake app attribution. Audit viewer allowlist remains unchanged (these operator events are not exposed through existing staff viewer). Audits contain no contact information, tokens or OTPs.

## Application interfaces

New module `src/modules/owner-setup/{types,policy,service,adapter,server,actions}.ts` and `components/owner-setup-manager.tsx`; route `src/app/(account)/account/owner-setup/page.tsx`. Existing styles reused/scoped. No shared motion-loop changes. Request-scoped official Supabase client, same-current-subject checks on every action, no global session/cache. Strict DTO validation and generic failure without private context.

Public actions:
- `checkOwnerSetupSessionAction(): Promise<OwnerSetupPageState>` no args, read-only self capability.
- `verifyOwnerSetupMfaAction(form: FormData): Promise<OwnerSetupActionResult>` exact subject+six-digit code only; server selects exactly one current self verified TOTP via existing MFA context/transport, and calls existing `performMfaOperation` with operation verify. Gate on native designation/current self before verification; do not expose enrollment/removal. No code echo/logging/return.
- `consentOwnerSetupAction(form: FormData): Promise<OwnerSetupActionResult>` exact subject, designation, confirm=`yes`; server-derived actor, database authoritative consent. Explicit checkbox/click, no automatic writes/retry or client approval/role selector.

`OwnerSetupPageState`: `{status:'guest'|'unavailable',message?:string}` or `{status:'ready',subject,phase:'mfa_required'|'ready'|'consented'|'completed',designation:string|null,intent?:{id,expiresAt}}`. Action result `{status:'success'|'error',message,reloadRequired?:boolean,state?:OwnerSetupPageState}`; never contains code/token/factor/session. Bind returned subject/designation to loaded/current context. Native state always re-read after any successful verification/consent. Uncertain writes require explicit reload, not optimistic success.

Manager props: `initial:OwnerSetupPageState`, `checkAction`, `verifyAction`, `consentAction` matching signatures above. Cleanup clears code/confirmation/intent/pending/errors and invalidates late work on account/designation change, pagehide and unmount/Activity. Development StrictMode setup can renew only fresh same-subject state; never auto verify/consent. Readiness refresh is read-only. Display that consent does NOT activate Owner and that operator approval remains separate. Default unselected state reveals no control/intent reference. Account navigation adds a neutral 'Owner setup' link for active Customers (no claim of eligibility); all real gates remain native.
